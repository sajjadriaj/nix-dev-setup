# nix-dev-setup

Reproducible developer workstation setup for Debian-based Linux distributions using Nix, Home Manager, and a small system bootstrap script.

The goal is to turn a fresh Debian or Debian-derived Linux installation into a ready-to-use development machine with one command.

## One-command setup

On a fresh Debian-based machine, run:

```bash
curl -fsSL https://raw.githubusercontent.com/sajjadriaj/nix-dev-setup/main/bootstrap.sh | bash
```

The bootstrap installs its own prerequisites, including Git, clones this repository to:

```text
~/.local/share/nix-dev-setup
```

and then installs/configures the workstation.

The only assumptions before running it are:

- Debian or a Debian-derived Linux distribution
- x86_64 architecture
- `bash`
- `apt-get`
- `sudo` configured for your user
- internet access
- systemd for Docker service management

After it completes, log out and back in once so Docker group membership takes effect.

You can override the checkout location:

```bash
curl -fsSL https://raw.githubusercontent.com/sajjadriaj/nix-dev-setup/main/bootstrap.sh \
  | DEV_SETUP_DIR="$HOME/dev/nix-dev-setup" bash
```

## Clone-first setup

If you prefer to inspect the repository before running anything:

```bash
git clone https://github.com/sajjadriaj/nix-dev-setup.git
cd nix-dev-setup
chmod +x bootstrap.sh
./bootstrap.sh
```

When run from a repository checkout, the bootstrap uses that checkout rather than creating another copy.

## What it installs

### System layer

`bootstrap.sh` handles software that needs host-level integration:

- bootstrap dependencies including Git and curl
- Nix in multi-user/daemon mode
- Docker Engine and systemd service
- Docker user group configuration
- base build dependencies through `apt`

### Nix / Home Manager layer

Persistent user tooling includes:

- VS Code
- Node.js 22 and pnpm
- Python 3.12 and uv
- Git, Git LFS, GitHub CLI
- tmux
- zsh, Starship, fzf
- GCC, Clang, CMake, Ninja, Make
- Docker Compose
- kubectl, Helm, k9s
- Terraform
- PostgreSQL and Redis clients
- protobuf and grpcurl
- HTTPie
- ripgrep, fd, jq, yq, bat, eza, tree, htop, btop
- networking/debugging tools
- hey and Vegeta for load testing
- direnv + nix-direnv

## Supported systems

The bootstrap targets **x86_64 Debian and Debian-derived Linux distributions** that provide `apt-get`, systemd, and the standard Debian package names used by the bootstrap.

It uses `/etc/os-release` and accepts systems identifying themselves as Debian or Debian-derived via `ID` / `ID_LIKE`; it does not special-case Ubuntu, Pop!_OS, or another derivative.

## Updating the workstation

For the default one-command installation:

```bash
cd ~/.local/share/nix-dev-setup
git pull
home-manager switch --flake ".#$USER"
```

Or simply rerun the bootstrap command. An existing managed checkout is updated with a fast-forward pull before the configuration is applied.

## Configuration layout

```text
nix-dev-setup/
├── bootstrap.sh   # Debian bootstrap, repo setup, Nix and Docker
├── flake.nix      # Nix/Home Manager entry point
├── flake.lock     # generated by Nix on first flake operation
├── home.nix       # persistent developer applications/configuration
├── .gitignore
└── README.md
```

## Why split bootstrap and Nix?

Nix/Home Manager manages reproducible developer tools and user configuration. Host-level concerns such as the Docker daemon, systemd integration, and initial Nix installation are handled through the small Debian bootstrap.

The bootstrap therefore does only enough system setup for Nix to take over most of the workstation configuration.

## Adding software

Add packages to `home.packages` in `home.nix`:

```nix
home.packages = with pkgs; [
  vscode
  nodejs_22
  python312
  uv
  # add packages here
];
```

Then apply:

```bash
home-manager switch --flake ".#$USER"
```

## Notes

- Currently targets x86_64 Debian-based Linux systems.
- VS Code is unfree software, so the flake enables `allowUnfree`.
- Application/project dependencies should generally remain in project-specific lockfiles (`uv.lock`, `pnpm-lock.yaml`, etc.) rather than this workstation configuration.
- Secrets, SSH private keys, cloud credentials, and project `.env` files should not be committed to this repository.
